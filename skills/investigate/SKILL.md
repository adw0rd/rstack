## Runtime rcode

Скилл — руководство, а не разрешение. Используй реальные инструменты rcode; вопросы пользователю задавай обычным текстом. В plan/read-only не вызывай shell или запись: явно укажи непроведённые проверки. Не переключай провайдера и не вызывай внешнюю модель без выбора пользователя. Не читай и не выводи ключи. Не выдумывай supporting files: используй только имена из resources ответа load_skill.

Цель — установить причину наблюдаемого сбоя проекта и, при подтверждении, применить минимальное исправление. Не публиковать без запроса; не коммитить по умолчанию.

## Порядок

1. **Воспроизвести.** Минимальный набор команд, детерминированно дающих ошибку. Точный текст ошибки (stdout+stderr), путь данных (какие файлы, какие env, какой промпт/инструмент), версии относящихся к сбою компонентов.
2. **Одна гипотеза.** Сформулировать ровно одну проверяемую гипотезу: «X происходит из-за Y, потому что Z». Подготовить эксперимент, который её подтвердит или опровергнет (изменение одного фактора, отладочный вывод, бисекция).
3. **Проверить.** Выполнить эксперимент, зафиксировать результат. Если опровергнута — собрать новые факты, сформулировать следующую гипотезу. Не строить цепочку угадываний: не более одной активной гипотезы.
4. **Минимальный фикс.** После подтверждения причины — наименьшее изменение, закрывающее именно её. Сохранять пользовательские изменения в рабочем дереве; не чинить «впопад» соседние места.
5. **Регрессия.** RED (тест FAIL до фикса) → фикс → GREEN (тест PASS + исходный сценарий PASS + соседний happy path).

## Ограничения

- Shell только при разрешении. Без shell — явно указать, что не проверялось; не называть «исправлено» непроверенное.
- Ключи не читать и не выводить.
- Субагенты: explorer/reviewer для чтения и ревью; worker только для изолированных файлов, не пересекающихся с текущим фиксом.

## Итог

Отчёт: причина (с доказательством), статус (исправлено / осталось), реальные команды и их выводы, RED/GREEN, ограничения и что осталось.
