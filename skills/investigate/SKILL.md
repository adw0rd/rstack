## Runtime rcode

Скилл — руководство, а не разрешение. Используй реальные инструменты rcode: в интерактиве основного агента (включая `/plan`) развилки постановки, которые нельзя разрешить чтением файлов и логов, уточняй через `ask_user` (1–3 вопроса, 2–4 варианта, рекомендуемый первым, без повтора в том же ходе и не для разрешений или секретов); в `exec`, без TTY и в субагентах пиши обычным текстом. В `/plan`, read-only ролях (`explorer`/`reviewer`) и при отказе оператора не вызывай shell или запись файлов: явно укажи непроведённые проверки; субагенты (`explorer`/`reviewer`/`worker`) также не имеют `ask_user`, памяти и `load_skill`. При включённой opt-in ОС-песочнице хоста (`--sandbox`, `/sandbox`) разрешённый оператором shell доступен, а в `--sandbox read-only` его запись ограничена приватным `TMPDIR` задания (скилл режим песочницы не меняет). `<rcode_memory_index>` и `read_memory` рассматривай как историческую справку, требующую сверки с текущими файлами; гипотезы и шаги расследования веди в `update_plan`, не вызывая `write_memory` (доступен только интерактивному основному агенту вне `/plan`) для временного состояния и секретов. Для локального воспроизведения на `localhost` / `127.0.0.1` / `[::1]` используй синтетические несекретные заглушки без секретных присваиваний, PEM, токен-префиксов (`sk-`, `ghp_`, `AIza`, `AKIA`) и `user:pass@`. Не переключай провайдера и не вызывай внешнюю модель без выбора пользователя. Не читай и не выводи ключи. Не выдумывай supporting files: используй только имена из `resources` ответа `load_skill`.

Цель — установить причину наблюдаемого сбоя проекта и, при подтверждении, применить минимальное исправление. Не публиковать без запроса; не коммитить по умолчанию.

## Порядок

1. **Воспроизвести.** Минимальный набор команд, детерминированно дающих ошибку. Точный текст ошибки (stdout+stderr), путь данных (какие файлы, какие env, какой промпт/инструмент), версии относящихся к сбою компонентов.
2. **Одна гипотеза.** Сформулировать ровно одну проверяемую гипотезу: «X происходит из-за Y, потому что Z». Подготовить эксперимент, который её подтвердит или опровергнет (изменение одного фактора, отладочный вывод, бисекция).
3. **Проверить.** Выполнить эксперимент, зафиксировать результат. Если опровергнута — собрать новые факты, сформулировать следующую гипотезу. Не строить цепочку угадываний: не более одной активной гипотезы.
4. **Минимальный фикс.** После подтверждения причины — наименьшее изменение, закрывающее именно её. Сохранять пользовательские изменения в рабочем дереве; не чинить «впопад» соседние места.
5. **Регрессия.** RED (тест FAIL до фикса) → фикс → GREEN (тест PASS + исходный сценарий PASS + соседний happy path).

## Ограничения

- Shell только при разрешении. Без shell — явно указать, что не проверялось; не называть «исправлено» непроверенное.
- Ключи не читать и не выводить.
- Субагенты: explorer/reviewer для чтения и ревью; worker только для изолированных файлов, не пересекающихся с текущим фиксом.

## Итог

Отчёт: причина (с доказательством), статус (исправлено / осталось), реальные команды и их выводы, RED/GREEN, ограничения и что осталось.
