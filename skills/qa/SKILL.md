## Runtime rcode

Скилл — руководство, а не разрешение. Используй реальные инструменты rcode: в интерактиве основного агента (включая `/plan`) неоднозначные развилки сценария, не решаемые чтением файлов, уточняй через `ask_user` (1–3 вопроса, 2–4 варианта, рекомендуемый первым, без повтора в том же ходе и не для разрешений или секретов); в `exec`, без TTY и в субагентах пиши обычным текстом. В `/plan`, read-only ролях (`explorer`/`reviewer`) и при отказе оператора не вызывай shell или запись файлов: явно укажи непроведённые проверки; ни один субагент (`explorer`/`reviewer`/`worker`) не имеет `ask_user`, памяти и `load_skill`. При включённой opt-in ОС-песочнице хоста (`--sandbox`, `/sandbox`) разрешённый оператором shell исполняется в её границах (в `--sandbox read-only` запись shell доступна только в приватный `TMPDIR` задания; если исправление или тест требуют записи вне допустимой области, честно зафиксируй границу без обхода). `<rcode_memory_index>` и `read_memory` — исторические данные: проверяй их по живым файлам, временный ход проверки веди в `update_plan`, а `write_memory` (доступен только интерактивному основному агенту вне `/plan`) не используй для баг-репортов и секретов. Не переключай провайдера и не вызывай внешнюю модель без выбора пользователя. Не читай и не выводи ключи. Не выдумывай supporting files: используй только имена из `resources` ответа `load_skill`.

Цель — проверить конкретный пользовательский сценарий проекта и, при нахождении бага, довести его до подтверждённого исправления с регрессией. Не публиковать без явного запроса; авто-коммитов нет.

## Подготовка

- Выбрать наблюдаемый сценарий и ожидаемый эффект (что видит пользователь / что должно появиться в файле / какой exit code).
- Изолировать данные и настройки: временный каталог, отдельный home, явный набор env. Не трогать живые данные пользователя. Для локальных проверок на `localhost` / `127.0.0.1` / `[::1]` используй только синтетические несекретные заглушки без токен-префиксов (`sk-`, `ghp_`, `AIza`, `AKIA`, `y0_`, `t1.`), PEM-блоков и `user:pass@` в URL.
- Не имитировать живые API фикстурами, выдавая их за живую проверку: явно отделять «живой прогон» и «фикстура» в отчёте.

## Проверка (не только модель)

- Ответ модели — не единственный сигнал. Проверить: файлы, которые должны создаться/измениться; exit code процесса; результат конкретного инструмента (write_file, run_command, search).
- Зафиксировать реальную команду и её вывод. Не называть пройденным то, что не запускалось.

## Если баг найден

1. Воспроизвести: минимальный набор команд, детерминированно дающий ошибку.
2. Использовать существующий тест, который воспроизводит баг, или добавить регрессионный тест при пробеле покрытия. Доказать FAIL на текущем состоянии (RED), сохранить вывод; не дублировать уже достаточную проверку.
3. Найти корневую причину (при необходимости загрузи rstack:investigate).
4. Исправить корень, а не симптом; не ослаблять корректный существующий тест ради GREEN.
5. Доказать GREEN: регрессионный тест проходит, исходный сценарий проходит, соседний happy path не сломался.

## Итог

Отчёт: сценарий, изоляция, наблюдаемый результат, баг (если есть), RED/GREEN с реальными выводами, что осталось. Если не удалось проверить часть — так и написать, без «вероятно работает».
