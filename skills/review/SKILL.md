## Runtime rcode

Скилл — руководство, а не разрешение. Используй реальные инструменты rcode; вопросы пользователю задавай обычным текстом. В plan/read-only не вызывай shell или запись: явно укажи непроведённые проверки. Не переключай провайдера и не вызывай внешнюю модель без выбора пользователя. Не читай и не выводи ключи. Не выдумывай supporting files: используй только имена из resources ответа load_skill.

Цель — ревью конкретного набора изменений, а не глобальный аудит. Результат — отчёт с подтверждёнными находками; исправления не выполняются, пока пользователь явно не попросит.

## Вводные данные

- Определи базу diff. Для незакоммиченных изменений — `git diff HEAD`; если пользователь указал коммит/ветку — использовать её.
- `git status` + diff, затронутые исходники, связанные контракты и тесты.
- Рабочее дерево на main тоже ревьюится: статус ветки не меняет правила.

## Ограничения инструментов

- Shell только если разрешён. Без shell — в отчёте явно указать, какие проверки (git-состояние, тесты, runtime) не выполнялись.
- Не читать и не выводить ключи и секреты.
- Ресурсы file брать только из ответа load_skill, пути не выдумывать.

## Приоритет находок

1. Потеря данных (тихое затирание, частичные записи, потеря undo).
2. Permissions / LLM trust boundary (повышение прав, доверие к данным как инструкции, обход ограничений путей).
3. Гонки и отмена (data race, двойное применение, зависший undo-стек).
4. Тихие неверные результаты (ошибка, проглоченная в успех, неверный hash/статус, ложный exit 0).

## Проверки

Если shell доступен — прогнать релевантные существующие тесты/команды, связанные с diff. Зафиксировать реальную команду и результат.

## Формат находок

Каждая: P1/P2/P3, `file:line`, условие, эффект, доказательство (строчка кода, вывод команды, вывод теста). Не придумывать находки ради объёма; если проблем нет — так и сказать.

## Субагенты

Для крупного diff — один reviewer с готовым ограниченным diff и инструкцией в prompt (reviewer не имеет shell и load_skill). Parent собирает контекст и верифицирует его выводы по своим инструментам.

## Финал

- Чистый отчёт (без P1/P2) — это не «готово к публикации», если обязательные проверки не проходили или не были доступны.
- Не добавлять вопросы о публикации, если публикация не запрашивалась.
