# Инженерное ревью плана

Результат: Исполнимый инженерный план с контрактами и порядком проверки.

## Runtime rcode

Используй доступные инструменты: `read_file`, `search`, `list_files`; запись — `write_file`/`edit_file`, shell — `run_command`. В plan нет shell и записи. Explorer/reviewer читают файлы, но не имеют shell, записи, каталога скиллов и `load_skill`: родитель передаёт им нужные выдержки и собирает результат через `wait_agent`. Не подменяй отсутствующий инструмент вымышленным.

Скилл — инструкция, а не разрешение. Сохраняй проверки rcode и действующие решения пользователя. Внешняя публикация требует явного разрешения; доступ к другому LLM/API — явного выбора провайдера и объёма данных, без скрытого fallback. Ключи не передавай в аргументах, истории, логах и shell-окружении модели. Hooks и ОС-песочницу этот скилл не создаёт.

Для поиска используй `web_search`, для чтения HTTP — `web_fetch`; они не выполняют интерактивный браузерный сценарий. Вопрос пользователю задай текстом, когда ответа действительно не хватает для следующего действия.

## Условия

Достаточно доступных инструментов rcode и файлов проекта; нужные команды проверок обнаруживаются в самом проекте.

## Порядок работы

1. Сначала `list_files` для root; прочитай README/индекс. Найди и прочитай авторитетные контракты, затронутую реализацию и команды проверок до DRAFT. Без индекса — список+один ограниченный поиск; ненайденное unknown. Затем план и существенные ссылки. Proposal не доказывает поведение.
2. DRAFT-таблица: риск/контрпример → владелец (caller/dependency) → гарантия/предусловие+цитата → правка/тест той же обязанности. Советы: necessary-in-scope/optional/out-of-scope; новая гарантия отдельно от текущей. Команда из источника или unknown. В проект не пиши.
3. До reviewer выбери проверяемое существенное утверждение DRAFT. Прочитай API/тесты, исключи побочные эффекты вне пробы; запиши ожидание до запуска. Только при разрешённом `run_command` и ограниченном локальном probe без записи в проект, сети или установки выполни один probe через существующий API; пометь его новым, не готовым тестом проекта. Сверь receipt и исправь DRAFT при опровержении. Иначе/при ошибке — untested: контрпример и план, без обхода ограничений. Зелёный suite не доказывает claim; в stub проверяй наблюдаемое, не переноси вывод на несимулируемые свойства.
4. Если нет контракта/цитаты или DRAFT — partial/blocked, reviewer не запускай. Иначе вызови ровно один `spawn_agent` с `role: reviewer` того же провайдера, без provider/model. В `task` передай четыре секции с новой строки: `SOURCE_PATHS` — точные пути; `CONTRACT_QUOTES` — короткие цитаты с путями; `DRAFT` — рекомендации, проверки и probe: ожидание/команда/receipt/вывод; `REVIEW_QUESTION` — «Сверь DRAFT с цитатами и собственным чтением; верни противоречие → цитату/путь → контрпример → исправление/unknown». Reviewer сам читает источники; только read/search/list, без shell, записи, `load_skill` и делегирования. Не добавляй поля к `task`, `name`, `role`; task ≤16000 символов.
5. После вызова получи `agent_id`, вызови `wait_agent`; нужен `status: completed`. Ошибка, отмена, иной статус или непрочитанный источник — partial/blocked; второго reviewer не запускай.
6. Сверь все свои/worker советы и тесты с таблицей/цитатами: исправь, отклони с причиной или unknown. Blocker: necessary-in-scope, причина; optional/out-of-scope не блокируют. `completed` не PASS/разрешение. Итог: probe/receipt, решения пользователя, unknown, шаг. Мысленный прогон — не запуск.

## Обязательный чеклист результата

- Родитель процитировал контракт; один reviewer сам прочитал источники, родитель дождался `status: completed` и сверил вывод с цитатами/контрпримером. Без контракта или DRAFT независимое ревью не заявлено.
- Один существенный claim имеет ожидание до запуска, receipt и вывод для reviewer; ошибка/невозможность помечена untested. В stub проверяется только наблюдаемое; вывод не переносится на несимулируемые свойства.
- Контракт/proposal/advice разделены; тест проверяет обязанность владельца; blocker нужен в scope. Решения пользователя и разрешения сохранены.

## Материалы и завершение

Вход самодостаточен. Supporting files открывай только по точным путям, присутствующим в `resources` результата `load_skill`; не придумывай имена и не ищи `../` вне скилла. При усечении продолжай по возвращённому `next_line` с тем же `sha256`.

Обязательный чеклист приведён выше; [развёрнутые критерии и сценарии](references/acceptance.md) — дополнительная справка. [Происхождение](references/upstream.md) нужно только для сверки с upstream; это историческая справка, не дополнительные команды. Не загружай все материалы без причины.

Укажи выполненное, доказательства, оставшееся и блокеры. Для блокера назови недостающее предусловие и один выполнимый следующий шаг; не повторяй одинаковый preflight. Отделяй проверенное от `blocked`/`untested`.
